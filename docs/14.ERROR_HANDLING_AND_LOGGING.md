# Error Handling & Logging

This document covers how RocketPHP handles exceptions and errors, and explicitly documents the current state of logging.

---

## 1. Exception Handling (`Kernel::handleException()`)

All exceptions thrown during the HTTP pipeline or route dispatch are caught inside `try { ... } catch (Throwable $e)` in [`Kernel::handle()`](../src/Foundation/Kernel.php) and passed to `Kernel::handleException(Throwable $e, Request $request)`.

### Status Code Resolution
- If `$e` defines `getStatusCode()` (e.g., `RouteNotFoundException` -> `404`, `MethodNotAllowedException` -> `405`, `ModelNotFoundException` -> `404`, `ValidationException` -> `422`), `Kernel` uses that status code if within `400..599`.
- All other exceptions default to HTTP `500`.

### Content Negotiation (`$request->wantsJson()`)
If the `Accept` header contains `/json` or `+json`:
- Returns `Rocket\Http\JsonResponse` with status `$statusCode`:
  - **Production (`$app->isProduction()` and `status === 500`)**:
    ```json
    { "error": true, "status": 500, "message": "Internal Server Error" }
    ```
  - **Non-production (or non-500 exceptions)**:
    Includes `'exception'` (FQCN), `'file'`, `'line'`, and `'trace'` (array of lines).
  - **Note:** `ValidationException` errors (`$e->getErrors()`) are **not** automatically appended to the JSON payload by `Kernel::handleException()`; only `$e->getMessage()` (`'The given data was invalid.'`) is included unless you catch `ValidationException` in custom middleware or a custom `Kernel`.

### HTML Error Responses
If the request does not ask for JSON:
- **Production + status `500`**: Renders generic `"500 - Internal Server Error"` HTML without exposing paths or traces.
- **Non-production (or status != 500)**: Renders a dark-themed HTML debug page showing escaped exception class, message, file, line, and stack trace.

## 2. Framework Exception Classes

| Exception Class | Status | Thrown When |
| :--- | :--- | :--- |
| `Rocket\Routing\Exceptions\RouteNotFoundException` | `404` | No route matches URI & method |
| `Rocket\Routing\Exceptions\MethodNotAllowedException` | `405` | URI matches another HTTP method (`getAllowedMethods()`) |
| `Rocket\Database\ORM\ModelNotFoundException` | `404` | `Model::findOrFail($id)` finds no row |
| `Rocket\Security\Validation\ValidationException` | `422` | `Validator::validate()` fails (`getErrors()`) |
| `Rocket\Container\NotFoundException` | `500` | `Container::make()` cannot find target class |
| `Rocket\Container\ContainerException` | `500` | Non-instantiable class, unresolvable param, invalid callback |

## 3. Logging Status (Important!)

- **No Framework Logger**: RocketPHP does **not** include a Logger class (`Logger`, `Log` facade, PSR-3 logger, or log channels). Although `storage/logs/.gitkeep` exists in the repository, nothing in `src/` writes log files there.
- **PHP Error Handlers**: Core does not override PHP's `set_error_handler()` or `set_exception_handler()`. Uncaught `Throwable` instances in HTTP requests are handled inside `Kernel::handle()`; PHP warnings/notices follow standard `php.ini` (`error_reporting`, `error_log`).
- **Database Query Log**: Only [`Connection`](../src/Database/Connection.php) provides an in-memory query log for debugging:
  ```php
  DB::connection()->enableQueryLog();
  // ... run queries ...
  $queries = DB::connection()->getQueryLog();
  ```
- **Adding Application Logging**: If an application requires structured file logging in `storage/logs/`, implement a custom service in `app/Services/` writing to `storage_path('logs/app.log')` via `file_put_contents(..., FILE_APPEND | LOCK_EX)` (or `error_log()`), and bind it in `AppServiceProvider`.
